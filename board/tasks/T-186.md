## Goal
Theo's idea: explorer bots that find every way through the dungeon and report. The fixed traversal test (tests/dungeon_traversal_test.gd) only walks route centre lines, so it misses snags off the line (thresholds, rubble hulls, parapet ends, gaps along walls, props). It drives the real player capsule; read it for the move/slide/snap loop and the 4x time scale. Build headless explorer bots that use the same capsule physics: (1) Sample the walkable space: a 0.5 m grid of downward rays over the dungeon bounds gives floor cells with an upward normal, 2 m of headroom and a slope under 45 degrees, grouped into areas (rooms from RedDescentLayout.rooms(), passages and bridges from RedDescentLayout.routes(); index.json in content/environments/procedural_architecture_v1 has stone passage coverage). (2) Several bots explore frontier-first: they walk with physics from reached cells to neighbouring unreached ones, without teleporting except to restart. They record reached cells, cells that are walkable but unreachable, stuck events (no progress for N seconds, with the slide collisions' collider paths and positions), falls (an unplanned drop over 2.5 m, with where they landed), ledges, and narrow chokepoints. (3) Travel times: walk between every pair of adjacent areas along the best found path. (4) Write telemetry JSON plus top-down heatmaps per level (reached, unreached, issues) as PNGs, and an issues list sorted by severity with the colliding node path. These names are the builder's (Collision_<room>_<n> stone cores, StonePassage_*, Props_*, Rubble_*), so each issue says which system to fix. Provide scripts/dungeon_explorer.py "" like the other tests, plus a fast mode for CI and a full mode. Do not change gameplay or level code; report the issues found to the T-185 owner (theo-claude-14).

### Theo's expanded requirements, 2026-10-26

The explorers are also a way to improve the environmental awareness and behavior of the gameplay bots. Collect enough context to explain a failure and actively try to expose problems; reaching sampled cells alone is insufficient.

- **Environment observations:** preserve every walkable level at an x/z position, connections between levels, slope, step/drop height, headroom, corridor width, floor/wall/ceiling contacts and relevant collider paths. Record discovered openings, obstacles, route alternatives and dead ends. Sample edges, thresholds, corners, stairs, bridge approaches and rubble, with finer probes around suspicious observations. A 0.5 m collision grid cannot certify centimetre-wide visual joints.
- **Gameplay behavior:** run scenarios using the actual enemy movement, navigation, perception and actor dimensions alongside the player-capsule coverage runs. Reuse `MobNavigation`, `HostileMob` and `RaiderMob` through their existing encounter setup. Record sensed obstacles and targets, line of sight, last-known target position and memory age, chosen goal/state, requested destination, returned path and endpoint, actual movement, collisions, progress and replans. Test following, losing and reacquiring a target around cover, returning home, blocked/unreachable goals, detours, narrow passages, stairs and stacked floors. Exercise crowd blocking and changed obstacles, reporting unsupported responses as limitations. Privileged map inspection must be labeled separately from what a gameplay bot actually sensed; it must not silently give the enemy hidden target positions or a better test-only navigator.
- **Active issue discovery:** deliberately try alternate approaches and directions, off-centre lanes and tight clearance; revisit failures with bounded deterministic trials. Flag falls, snags, repeated failed routes, oscillation, prolonged lack of progress, wrong-floor goals, incorrect arrival, unsafe edge/attack approaches, and visibility/collision contradictions. Preserve the action and recovery attempts as well as the outcome. Distinguish an intentional territory limit, ruin opening or valid dead end from a suspected defect. State the evidence and confidence; a heuristic flag is not a verified bug.
- **Visible surfaces and geometry:** add a distinct render-mesh/screenshot audit for see-through floor and ceiling joints, missing backing, normals/backface errors and mismatches between visible surfaces and collision. Physics-only rays and capsule success cannot clear these checks. Trace candidates to room/module/builder and capture them through `scripts/godot_bg.sh`. Collect per-section mesh, surface, triangle and instance counts; report buried/duplicate geometry as candidates until inspected. Rendering cost requires an actual rendered measurement, separately from headless timings. Start with the reported floor and ceiling gaps.
- **Reproduction and comparison:** every issue needs build/layout identity, seed, actor profile, room/level, world position, involved node paths, expected and observed behavior, a replay command/scenario, and a short event trace; visual issues also need a capture/view. Aggregate coverage, arrival success, route efficiency, travel time, stuck duration, falls, replans and recovery success, keeping player and enemy results separate. List checks that did not run or cannot yet detect an issue as unchecked. Save bounded traces around incidents rather than unlimited per-frame logs.
- **Feedback into gameplay bots:** turn reproducible failures into regression scenarios for the real enemy code. Compare the same seeded scenarios before and after each navigation/perception/recovery fix, including cover, floor separation and authority checks. Better explorer coverage is not evidence of better enemies: report their measured outcomes independently. Runtime fixes belong in separately claimed scopes for the owning gameplay files; this task's existing scope remains the explorer harness and reports. Report map defects on T-185 and file actionable gameplay follow-ups with their replay evidence.

Current source observations to exercise, not reproduced failures: `MobNavigation` stores one surface per grid cell; the dungeon uses two height-bounded room grids (`gameplay/mobs/dungeon_mobs.gd`). `HostileMob.walk()` returns true when its route is empty, and its arrival and waypoint checks use horizontal distance (`gameplay/mobs/hostile_mob.gd`). The harness must distinguish arrival from no route, a partial route ending short, and a goal on another floor.

## Done when
- Explorer runs headless, produces telemetry JSON, heatmaps and an issues list for the current dungeon; docs/dungeon-explorer.md explains it; findings are reported on T-185.
- A documented capability list separates physics, gameplay behavior, rendered inspection and geometry checks, including unchecked capabilities and coverage limits.
- Deterministic known-defect and valid-control scenarios verify the implemented detectors: blocked/unreachable goals versus arrival, stacked floors, stuck movement, cover/target memory, and a visible gap over solid collision. Document detector limits rather than claiming all issues are discoverable.
- At least one end-to-end gameplay-bot failure has a replayable scenario, decision trace and actionable follow-up. The same harness can compare the real bot before/after a scoped fix without changing the scenario or granting it extra information. A failure not found in a run is reported honestly rather than manufactured.
- Floor/ceiling findings include rendered evidence; headless traversal success alone does not close visual defects. Geometry counts do not stand in for measured performance.
